## Findings, ordered by priority

### R1 — P1: ordinary multi-megabyte attachments abort the entire export

Location: `src/parsers/enex/convert.js:11`, `decodeData`.

The repeated-group base64 regular expression exhausts the JavaScript regexp stack on valid input. A 4 MiB resource produces a roughly 5.6 MB ENEX file, far below the documented 128 MiB per-note character limit, yet the CLI exits 1 with `Maximum call stack size exceeded`. The 8 MiB probe fails identically. The direct API stack trace identifies `RegExp.test` at `decodeData`, not XML nesting or the configured note limit. Small 64 KiB and 1 MiB controls succeed and their stored bytes match the independently generated input.

Impact: a normal photo, PDF or other attachment can prevent an otherwise valid notebook export from producing any archive. Source files remained unchanged and no completed archive was published in the failing probes.

Repair: replace the unbounded repeated-group pattern with bounded/linear alphabet and padding checks, retaining canonical round-trip validation. Add regression cases of at least 4 MiB and 8 MiB, including invalid padding and late invalid characters. Do not solve this by increasing the process stack.

Evidence: `.evidence/review-20261123-probes.json`, `.evidence/review-20261123-fidelity.json`; retained generated input files are named in those reports.

### R2 — P1: style-based Evernote checklists silently lose normalized states

Location: `src/parsers/enex/convert.js:67`, checkbox conversion.

Only `en-todo` elements become checkbox nodes. Evernote exports also represent checklists using a `ul` with the `--en-todo` style property and `li` elements with `--en-checked`. This pattern is present in a [firsthand exported sample in Joplin issue 7329](https://github.com/laurent22/joplin/issues/7329), identified there as Evernote 10.49.4. That is evidence for this source representation, not a claim about every current Evernote build.

A synthetic two-item probe using that representation exits 0 but produces `checkboxes: []`, no checkbox nodes, plain text without state markers, and no note-specific warning. The expected states are `[true, false]`. Original ENML and raw style attributes survive, so this is normalized semantic loss, not destruction of the original source.

Impact: a future reader/importer consuming the neutral checkbox fields cannot distinguish checked and unchecked items. This contradicts the broad checklist-preservation claim and affects a central migration requirement.

Repair: recognize the checklist container and per-item checked property, preserve item order and nesting, and emit a warning or unknown state for malformed representations. Test both legacy `en-todo` and style-based lists, including nested lists and non-checklist list items.

Evidence: `modern-checklist` in `.evidence/review-20261123-fidelity.json`.

### R3 — P2: verification accepts records missing required semantics

Locations: `src/core/storage/archive.js:160`, `:164`, `:174`.

The verifier validates some fields but skips required encrypted-node fields and redundant semantic fields. It returns `valid: true` after each of these independent mutations: deleting an encrypted node's `ciphertext`; replacing the checkbox summary with a nonboolean state inconsistent with the document tree; changing an attachment's MD5 to an unrelated value.

The probes deliberately recompute the changed note's size and SHA-256 in the manifest. These are **schema/producer-defect simulations**, not evidence that checksums should authenticate an attacker-controlled manifest. Byte-integrity checks are behaving as designed; the missing gate is structural and semantic validation.

Impact: the exporter calls this same verifier before publication, so internally inconsistent producer output can pass its publication check. Future readers cannot safely treat `valid: true` as confirmation of the documented version-1 note contract.

Repair: validate required fields for every content-node type; reconcile the checkbox summary against tree order and states; validate attachment metadata and media references against actual asset bytes. Keep checksum validity, schema validity, source reconciliation and account completeness distinct in the result.

Evidence: `checkbox-summary`, `attachment-md5` and `encrypted-ciphertext` in `.evidence/review-20261123-probes.json`.

### R4 — P3: the plain-text projection merges distinct content

Location: `src/parsers/enex/convert.js:59` and newline handling later in `convert`.

Two consecutive `br` elements collapse into one newline; neighboring table cells have no separator. The independent probe produces `First\nThird\nLeftRight` from a blank line followed by distinct `Left` and `Right` cells. The original ENML and ordered document tree remain intact. The format already calls plain text a convenience projection, so this is lower priority than R1/R2, but merging cells changes readable text, not merely decoration.

Repair: preserve explicit line breaks and delimit table cells/rows in the projection. Test blank paragraphs, consecutive breaks and tabular text before using this field for search snippets or target export.

Evidence: `linebreaks-and-table` in `.evidence/review-20261123-fidelity.json`.

## Repository coverage and remaining limits

Reviewed all six runtime JavaScript files, package manifest/lock, the test suite and fixture, README, format specification, verification record, task state, ignore rules and local project guidance/settings. No native/mobile/web sources or implemented target adapters were found; exporter/model directories still contain scaffolding placeholders. This was a single-worker review with separate adversarial probes, not an independent human or second-agent review.

- `src/cli.js`: exposes only export/verify; basic argument rejection is tested. No account capture, browser integration, multi-file capture or importer.
- `read.js` / `xml.js`: streaming UTF-8 input, single-note trees, fatal decode errors, nesting limit and rejected internal DTD subsets. No network-based entity resolution found. Per-note buffering and duplicated ENML/JSON/resource material still require memory qualification for larger workloads.
- `convert.js`: exact original source is retained, but the conversion defects above prevent general fidelity claims. Structured Tasks, reminders, recognition and alternate data are retained as metadata rather than fully normalized features, as documented.
- `archive.js`: exclusive destination creation, staged verification and `.incomplete` marker; existing destinations and junction/traversal rejection are tested. No disk-full, forced termination or power-loss durability test was performed. No atomic whole-directory publication claim is made.
- Tests: all **23 existing tests passed** on this review run. The new probes reproduce failures outside their coverage. The existing larger-input test exercises chunk boundaries but does not cover multi-megabyte resources.
- Dependencies: pinned direct versions and lockfile inspected. `npm audit --omit=dev` reported **0 known advisories** at review time; this does not establish absence of vulnerabilities. No production dependency changed.
- Packaging: `npm pack --dry-run` contains local `.claude/settings.local.json`, assistant guidance, tests and task state. No package was created or published. Before distribution, add an intentional package file allowlist; the local settings inspected here contain permissions, not credentials.

An additional probe removes all note records and derived payload entries from the manifest while retaining the original two-note ENEX. `verify` accepts the resulting zero-note inventory. The documentation explicitly excludes independent source reconciliation, so this is recorded as a **known qualification gap**, not a checksum defect. A complete-backup claim needs independent source counts and feature reconciliation, not only manifest self-consistency.

## Recommended sequence

Repair R1 and R2 first, strengthen verification for R3, then address R4. Add an explicit multi-notebook capture format and a usable reader/export adapter before qualifying a migration. For phone access, choose a mobile-capable reader or application and test the actual transfer/open/read/attachment journey on the target device. For Evernote compatibility, obtain a representative export from the target desktop build, reconcile expected notes and features independently, then test the intended destination route. None of these implementation or live acceptance steps was performed by this review.
